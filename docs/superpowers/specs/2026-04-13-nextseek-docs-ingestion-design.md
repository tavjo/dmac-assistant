# NExtSEEK Docs Ingestion — Design Spec

**Date:** 2026-04-13
**Project:** DMAC Assistant POC
**Status:** Revised after adversarial review and endpoint-behavior spike

---

## 1. Problem

The DMAC Assistant runs Claude Code in a container and lets users ask natural-language questions about NExtSEEK workflows. For the agent to answer accurately, it needs access to the NExtSEEK documentation published at `https://koch-institute-mit.gitbook.io/mit-data-management-analysis-core/`. Loading the entire GitBook into the agent's context on every session would be wasteful: most conversations touch only a small slice of the docs, and per-session token cost scales with every user.

We need a way to expose the docs such that:

- The agent always knows NExtSEEK docs exist and how to find them.
- The agent only loads detail for the sections it actually needs.
- The solution does not add a runtime network dependency or startup latency.
- The solution does not introduce a new LLM dependency in the build/ingestion pipeline.
- The solution respects DMAC's existing architectural invariants (ADR-002 Docker-as-isolation-boundary, ADR-005 secrets-only-in-env, ADR-008 plugin taxonomy).

## 2. Non-Goals

- A retrieval plugin the agent invokes at query time. The built-in `Read` tool is sufficient; a search/grep/embedding tool is not.
- An MCP server. Same reason — unnecessary for this POC.
- Generalized "ingest any docs site" machinery. NExtSEEK-specific for the POC; generalize later only if a second doc source appears.
- Automatic doc-change detection on a cron. Manual-trigger only for the POC.
- Network-based fetch at `docker build` time or container start time.

## 3. Architecture

A **build-time ingestion tool** — not a plugin (ADR-008 reserves "plugin" for runtime CLI tools the agent invokes). Ingestion is a one-shot script run by a developer via a Makefile target when NExtSEEK docs may have changed. Its output is committed to git. The Docker image build copies the already-generated files.

### Two CLAUDE.md files, different audiences

There are intentionally two `CLAUDE.md` files in the repository with different purposes:

- **`CLAUDE.md`** (repo root) — guidance for Claude Code sessions doing development work on the DMAC repo itself. Dev-side audience. Never baked into the container image.
- **`container/CLAUDE.md`** — the in-container agent's instruction file. Baked into the Docker image as `/app/CLAUDE.md`. The NExtSEEK block inside this file is auto-generated by the ingestion tool; everything else is authored by humans.

```
developer runs: make ingest-nextseek-docs
  │
  ├─▶ fetch GitBook URL (httpx)   [returns HTML; see §4.1 note]
  ├─▶ markitdown → raw markdown string  [auto-detects HTML, preserves <h1> as #]
  ├─▶ sha256(raw) ─── compare with docs/nextseek/.content-hash
  │                   │
  │                   ├─ same ──▶ exit 0, print "no changes"
  │                   │
  │                   └─ different:
  │                        ├─▶ split by H1 → per-section .md files
  │                        ├─▶ regenerate docs/nextseek/README.md (TOC)
  │                        ├─▶ regenerate NExtSEEK block in container/CLAUDE.md
  │                        ├─▶ write new .content-hash   [LAST write; see §7]
  │                        └─▶ exit 2 (signal: rebuild image)
  ▼
developer reviews git diff, commits, rebuilds image, pushes
```

### Runtime Behavior Inside the Container

1. `/app/CLAUDE.md` contains a 3–5 line NExtSEEK summary block so the agent knows the docs exist, has a quick top-level mental map, and knows the entry point for detail is `/app/docs/nextseek/README.md`.
2. When a user asks something NExtSEEK-related, the agent uses its built-in `Read` tool on `/app/docs/nextseek/README.md` to see the TOC.
3. The agent picks a section based on TOC descriptions and `Read`s the specific `/app/docs/nextseek/<slug>.md` file.
4. No runtime plugin invocation, no network call, no Bedrock call, no secret — just file reads on a path that's already baked into the image.

## 4. Pipeline Detail

### 4.1 Fetch

Port `fetch_pdf_content` from `smart-form-tool/packages/core/src/smart_form_core/utils/nextseek_docs.py` **verbatim** (lines 123–137). Rename to `fetch_source_bytes` to reflect reality.

```python
DEFAULT_DOC_URL = (
    "https://koch-institute-mit.gitbook.io/mit-data-management-analysis-core/"
    "~gitbook/pdf?limit=100"
)

def fetch_source_bytes(url: str) -> bytes:
    with httpx.Client(timeout=120.0, follow_redirects=True) as client:
        response = client.get(url)
        response.raise_for_status()
    return response.content
```

**Observed behavior (verified 2026-04-13):** GitBook's `~gitbook/pdf?limit=100` endpoint returns ~1.3 MB of `text/html; charset=utf-8` — a client-side PDF viewer page, NOT raw PDF bytes. The example projects' function name (`fetch_pdf_content`) is misleading. Downstream (`parse_source_to_markdown`) works because markitdown auto-detects content type from bytes and handles HTML transparently.

Override via `NEXTSEEK_DOC_URL` env var for testing.

### 4.2 Parse

Port `parse_pdf_with_markitdown` from smart-form-tool verbatim (lines 140–169). Rename to `parse_source_to_markdown`.

```python
def parse_source_to_markdown(source_bytes: bytes) -> str:
    with tempfile.NamedTemporaryFile(suffix=".pdf", delete=False) as f:
        f.write(source_bytes)
        temp_path = f.name
    try:
        md = MarkItDown()
        result = md.convert(temp_path)
        return result.text_content
    finally:
        os.unlink(temp_path)
```

Uses `markitdown[all]` to match the example projects' dep footprint. The `.pdf` suffix is a historical artifact — markitdown auto-detects content by sniffing bytes, so HTML content in a `.pdf`-named tempfile is parsed as HTML and `<h1>` tags become `# ` markdown headings.

**Verified output on the real GitBook URL:** ~71,200 characters of markdown with proper `#` and `##` heading structure preserved.

### 4.3 Change Detection

```python
content_hash = hashlib.sha256(raw_markdown.encode("utf-8")).hexdigest()
hash_path = Path("docs/nextseek/.content-hash")
if hash_path.exists() and hash_path.read_text().strip() == content_hash:
    sys.stdout.write("no changes\n")
    sys.exit(0)
```

`--force` bypasses the early exit and always regenerates.

### 4.4 Split by H1 (fence-aware)

Parse the markdown line-by-line with a **code-fence-aware tokenizer**. Maintain a `inside_fence` boolean that toggles on lines matching `^\s*```` (three backticks). A line matching `^# \S` outside a fence opens a new section. Inside a fence, `#` lines are ignored (they are shell comments, python comments, etc., not headings).

Filename slug rules:
- Lowercase the heading text.
- Replace any run of non-alphanumeric characters with a single `-`.
- Strip leading/trailing `-`.
- Prefix with a zero-padded 2-digit ordinal matching the section's order in the source: `01-welcome.md`, `02-getting-started.md`, etc.
- If two H1s slug-collide, append a `-N` suffix with N=2,3,... until unique across the current run.

Write each section's body (including the H1 line) to `docs/nextseek/<ordinal>-<slug>.md`. Before writing any section files, delete any existing `docs/nextseek/*.md` files *except* `README.md` and `.content-hash` — stale section files from removed GitBook pages must not linger.

### 4.5 Per-Section One-Line Descriptions

For each section, the description is the first non-empty paragraph after the H1, truncated to ~140 characters at a word boundary if longer. A "paragraph" here is content up to the first blank line. If the section has no body text before the next heading, the description falls back to the literal string `(section overview)`. If the description has no word boundary within 140 chars, truncate at the closest preceding whitespace and append `…`.

### 4.6 Generate `docs/nextseek/README.md`

```markdown
# NExtSEEK Documentation — Table of Contents

_Generated by build_tools/ingest_nextseek_docs. Do not edit by hand._

Source: https://koch-institute-mit.gitbook.io/mit-data-management-analysis-core/
Content hash: <first 12 chars of sha256>

## Sections

- **[Welcome](01-welcome.md)** — <one-line description>
- **[Getting Started](02-getting-started.md)** — <one-line description>
- ...
```

### 4.7 Update the NExtSEEK Block in `container/CLAUDE.md`

The baked `container/CLAUDE.md` contains a delimited block that the ingestion tool rewrites in place. Marker strings are centralized as module constants in `build_tools/ingest_nextseek_docs/constants.py`:

```python
BEGIN_MARKER = "<!-- BEGIN NEXTSEEK-DOCS (auto-generated) -->"
END_MARKER = "<!-- END NEXTSEEK-DOCS (auto-generated) -->"
```

`container/CLAUDE.md` contains (after skeleton authoring):

```markdown
<!-- BEGIN NEXTSEEK-DOCS (auto-generated) -->
## NExtSEEK Documentation

<first paragraph of the first H1 section from the GitBook — verbatim>

Top-level sections: Welcome, Getting Started, Sample Registration, ...

For detail, read `/app/docs/nextseek/README.md` first.
<!-- END NEXTSEEK-DOCS (auto-generated) -->
```

The updater reads the file, locates the markers via exact string matching (not regex), replaces the content between them, and writes back **atomically** (write to `<path>.tmp` then `os.replace`). If either marker is missing or appears more than once, raises `ValueError` with a clear message. The updater never appends a new block — double-injection is impossible by construction.

The prose paragraph is verbatim from the first H1 section's first paragraph — typically a GitBook "Welcome" or "Introduction" page written specifically to summarize the space. No LLM involvement.

### 4.8 Exit Codes and Logging Contract

- `0` — no changes (hash matched). Message `no changes` written to stdout.
- `1` — error. Error message written to stderr; no partial writes (see §7).
- `2` — changes written; image rebuild needed. Summary of changed files written to stdout.

Logging uses Python's `logging` module configured to write to stderr at INFO level. stdout is reserved for the human-readable status line(s) that the Makefile reads.

## 5. Components

| Module | Responsibility |
|---|---|
| `build_tools/ingest_nextseek_docs/constants.py` | `BEGIN_MARKER`, `END_MARKER`, `DEFAULT_DOC_URL`, `DEFAULT_DOCS_DIR`, `DEFAULT_CLAUDE_MD_PATH`. Single source of truth for magic strings. |
| `build_tools/ingest_nextseek_docs/fetch.py` | `fetch_source_bytes(url) -> bytes`; `parse_source_to_markdown(bytes) -> str`. Ported verbatim from smart-form-tool (renamed only). Must not import `baml`, `duckdb`, `smart_form_*`, or anything clustering/embedding-related. |
| `build_tools/ingest_nextseek_docs/split.py` | `Section` dataclass (ordinal, title, slug, body, description); `split_by_h1(markdown) -> list[Section]`. Fence-aware. Pure function. |
| `build_tools/ingest_nextseek_docs/hashing.py` | `compute_content_hash`, `read_stored_hash`, `write_stored_hash`. |
| `build_tools/ingest_nextseek_docs/toc.py` | `render_readme(sections, source_url, content_hash) -> str`; `render_claude_md_block(sections, overview_paragraph) -> str`; `update_claude_md(path, block_content) -> None` (atomic). |
| `build_tools/ingest_nextseek_docs/__main__.py` | `ingest(*, docs_dir, claude_md_path, doc_url, force, fetcher=fetch_source_bytes, parser=parse_source_to_markdown) -> int`. Argparse wrapper with production defaults. **Fetcher and parser are dependency-injected** to keep tests honest. |
| `Makefile` target `ingest-nextseek-docs` | Runs the CLI, prints a post-run status message on exit 2. |

Each module is independently testable. `fetch.py` is the only module with a network dep; the rest are pure functions over strings and paths.

## 6. Testing

**Fixture strategy (revised):** Synthetic HTML (pure-string generator, no binary or heavyweight dep). Because the real GitBook fetch returns HTML and markitdown handles HTML natively, HTML is the authentic content format to test against. No reportlab, no PDF synthesis.

Helper in `tests/conftest.py`:

```python
def make_synthetic_html(sections: list[tuple[str, str]]) -> bytes:
    """Build HTML with real <h1> + <p> elements for the given (title, paragraph) pairs."""
    body = "\n".join(
        f"<h1>{title}</h1>\n<p>{para}</p>" for title, para in sections
    )
    return f"<!DOCTYPE html><html><body>{body}</body></html>".encode("utf-8")
```

**Autouse production-path guard** in `tests/conftest.py`: an autouse fixture monkeypatches `build_tools.ingest_nextseek_docs.__main__.DEFAULT_DOCS_DIR` and `DEFAULT_CLAUDE_MD_PATH` to sentinel paths that raise `RuntimeError` if used. Any test that accidentally calls `ingest()` without passing `tmp_path` overrides fails loudly instead of polluting the repo.

**Layers:**
- **Unit** (`tests/unit/`): one file per module. Each module's pure functions covered with per-case assertions (not count-based). Fetcher and parser stubs used for `__main__.ingest()` via dependency injection.
- **Integration** (`tests/integration/`): `test_end_to_end.py` runs the full pipeline with `synthetic_html` bytes as the fetcher's return value. Covers: fresh ingest writes expected files; re-ingest exits 0; mutated source deletes stale sections.
- **Contract** (`tests/integration/test_markitdown_contract.py`): single test that asserts `MarkItDown().convert(...)` preserves `<h1>` from a synthetic HTML fixture as `# ` in its markdown output. Pins the assumption that the whole plan rests on; if markitdown changes this behavior in a future version, this test fails fast.
- **Smart-form-tool import gate** (`tests/unit/test_no_stale_imports.py`): greps `build_tools/` and asserts no imports of `baml`, `duckdb`, `leiden`, `smart_form_*`, or `openai`.

**Network isolation:** `pytest-socket` disables all sockets by default; any test that wants a real HTTP call must explicitly enable it (no integration test does).

## 7. Error Handling and Atomicity

- Network failure on fetch: log to stderr, exit 1. No writes occur because the write phase hasn't started.
- markitdown failure: log with preserved input, exit 1.
- Zero H1 sections in parsed markdown: log error ("probable markitdown output change — investigate before committing"), exit 1.
- Missing or duplicated markers in `container/CLAUDE.md`: raise `ValueError` from `update_claude_md`; caller converts to exit 1 with a message pointing at the one-time skeleton setup.

**Write ordering for atomicity:** All file writes in the regeneration phase follow this order, ensuring the hash file is NEVER stale-ahead-of-content:
1. Delete stale `docs/nextseek/*.md` (except `README.md`, `.content-hash`).
2. Write each new per-section `docs/nextseek/<slug>.md`.
3. Write `docs/nextseek/README.md`.
4. Write `container/CLAUDE.md` atomically (tmpfile + `os.replace`).
5. **Last:** write `docs/nextseek/.content-hash`.

If any step fails, the hash was never updated, so the next run re-detects "changed" and regenerates. Partial state is always self-correcting.

## 8. Invariants Preserved

- **ADR-002 (Docker-as-isolation-boundary):** Docs are baked into the image. The container has no new mount, no new network route.
- **ADR-005 (secrets-only-in-env):** No secrets involved anywhere — the GitBook is public.
- **ADR-008 (plugin taxonomy):** This is a build-time tool, explicitly not a plugin. The runtime plugin directory stays untouched.
- **ADR-012 (`--dangerously-skip-permissions` safety):** The agent's new capability is reading baked-in files under `/app/docs/` — read-only data inside the container's already-bounded blast radius.

## 9. Open Items (POC Scope)

- **Who triggers ingestion and rebuild?** Manual for POC. A CI job that diffs the GitBook weekly and opens a PR is a reasonable post-POC addition but out of scope here.
- **What if a section is very large (>50KB)?** Accept as-is for POC. The agent's `Read` handles large files fine. If in practice a single page dominates context, revisit with an H2 sub-split for that section only.
- **What about IGB and internal BMC documentation that smart-form-tool also ingests?** Deferred. NExtSEEK only for POC. Adding more sources later is additive — new ingestion target, parallel output tree under `docs/`, additional CLAUDE.md block with a different marker pair.
- **What if GitBook changes the endpoint contract (e.g., starts returning PDF again, or requires auth)?** The markitdown contract test (§6) will catch content-type regressions. Fetch-layer changes would surface as exceptions from `fetch_source_bytes`.
