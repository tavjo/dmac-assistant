1. Executive summary

The goal is a demo-day dry run: drive the NExtSEEK batch-upload skill end to end through the browser chat UI, screenshot the flow, and land a valid upload workbook in the operator's Dropbox example-project folder. Two turns: an NExtSEEK-routed question that retrieves a scientist's samples, then a Claude-Code-routed follow-up that builds a sheet setting Scientist = Jane Doe on those UIDs.

Everything needed already exists. The skill is built, merged, and live-proven for the create path by six paid end-to-end turns. The chat UI, the WebSocket bridge, the LLM router, and the post-turn Dropbox copier are all implemented. Nothing in this demo writes to NExtSEEK: the skill builds and validates a spreadsheet and is hard-blocked from uploading (SKILL.md:73-77; every shim exits 3 on --start|--upload|--confirmed-write).

Three findings shape the plan. (1) The create path is fully live-proven, and the Dropbox delivery mechanism is proven along with it: bundle 20260707T231422Z carries payload_flat.xlsx byte-identically on both sides of the copier (6467 B, sha256 23e8fb19…). What is not proven is the update path — exactly what this demo shows. Every rows.json across all six paid bundles has an empty UID, so no populated-UID row has ever been driven by a live agent turn. It is safe, but can fail-closed on one of three gates. (2) Route selection is decided by an LLM and cannot be forced; empirically, batch-upload phrasing lands on container_cc every time, because the router's own capability text names an upload_payload family whose example is literally "Build an update payload to fix the metadata on these existing samples." (3) Dropbox publishing works, but the destination is governed by DMAC_OUTPUT_ROOT, which is set in no env file and silently falls back to ~/dmac-dev/output — a default no operator ever chose. The operator already locked the correct design on 2026-05-28; that build was deferred.

4 open decisions: 3 BLOCKER, 1 DEFAULTABLE. None require code changes — the demo runs entirely on existing code plus environment configuration.

2. Project purpose as inferred from evidence

DMAC Assistant wraps Claude Code as the agent runtime for MIT BioMicro Center lab users: a thin FastAPI bridge authenticates a user, mounts their project directories, starts a per-user Docker container, and relays a chat turn to a containerized claude CLI (.claude/CLAUDE.md "What This System Is").

The batch-upload skill is one capability inside that container. Its purpose is narrow and explicitly bounded: "You prepare a flat create/update workbook and validate it. You do not submit it. The safe output is the workbook path plus the validation result." (build_context/plugins/nextseek/skills/nextseek-batch-upload/SKILL.md:9-12).

This scout run's purpose is not to change any of that. It is to determine exactly how to demonstrate it through the UI, with the artifact delivered to Dropbox, and to surface where that demonstration could fail.

5. What the code already implements

Built and live: the chat UI and its dmac.bearer-subprotocol WebSocket (index.html:628, ws.py:104,142-156); the BAML router, on by default (ws.py:830-844 — DMAC_ROUTER_ENABLED defaults to "1"); the canned unrelated reply (ws.py:89-95, 1065-1083); the six batch-upload shims; the workbook builder; and the post-turn copier.

Built but mis-pointed: the copier writes output_root/<user_id>/<rel> (copier.py:57-58,72). output_root resolves from DMAC_OUTPUT_ROOT (config.py:215-218), which appears in no env file — verified across .env, .env.dev, .env.example, .env.prod, the whole working tree, and git log --all -S'DMAC_OUTPUT_ROOT'. It therefore falls back to _DEV_DEFAULT_OUTPUT_ROOT = ~/dmac-dev/output (config.py:19). The only assignment anywhere in the repo is README.md:106, which is stale against the 2026-05-28 locked decision.

Designed, not built: the <project>/<user>/<session>/{raw,artifacts} hierarchy. The operator reports it is already implemented correctly in the integrated NExtSEEK version, which is the long-term target.

Not implemented at all: any mechanism to force a route. Grep for force_route|route_override|DMAC_ROUTE across src/ returns nothing. DMAC_ROUTER_ENABLED=0 disables routing entirely rather than selecting a route.

6. What the tests already cover

The three update-path fail-closed gates are covered by unit tests only: tests/unit/test_batch_upload_runner.py:354 (assay_superset), :368-374 (confirm_clear_assays scoping), :221 (present_blank), and tests/unit/test_batch_upload_payload.py:200-201 (present_blank:Treatment).

The T10 harness (tools/e2e/batch_upload_live_evidence.py, verify_batch_upload_live.py, run_batch_upload_live_e2e.py) carries 115 hermetic tests at 100%/99% module coverage, plus a $0 verifier that recomputes the verdict and cost from the raw transcript. Post-merge suite: 121 tests + pin registry, 68 green.

The coverage gap that matters here: no test — hermetic or paid — drives an agent-orchestrated update turn against the current skill. The hermetic tests hand-write the confirmation token, which is precisely why they never caught the live --name resolution defect that the paid runs did.

8. Local research methods

All repository inspection was read-only; no project file was modified or deleted. Methods:

  • Two parallel read-only Explore agents over the skill/evidence and the bridge/UI/routing/delivery surfaces, then independent re-verification by hand of every load-bearing claim — one agent summary (that Dropbox delivery had never worked via the bridge) turned out to be wrong and was corrected against ls -lT of the Dropbox tree.
  • git log --all -S'DMAC_OUTPUT_ROOT' and a whole-tree grep to establish that the variable is assigned in exactly one place (README.md:106).
  • docker ps -a, docker images, docker network ls to establish the runtime prerequisites.
  • Live read-only probes of nextseek-dev.mit.edu with explicit controls: anonymous → 401, deliberately-wrong credentials → 401, .env credentials → 200. This eliminated the assumption that a 200 proved the credentials were doing anything.
  • The sanctioned nextseek-api skill could not bootstrap (its SchemaRAG ingest against dev times out; the operator confirms a container-side issue). Per operator instruction the dev OpenAPI schema was fetched directly (GET /nextseek_api/schema/?format=yaml, 287 KB, OpenAPI 3.1.0, 49 paths) into a temp dir and inspected locally with uv run --with pyyaml.
  • Reproducible evidence persisted at docs/research/fixtures/2026-07-09-dev-tis-scientists.json.

13. Data model or interface summary

Rows JSON (the skill's input, SKILL.md:43-46): a list of {UID, SampleType, attributes{}, assay_ids?|assay titles?}. Blank UID creates; populated UID updates. Values live in attributes; the tools synthesize the canonical json_metadata. The UID column and json_metadata.UID must agree.

Workbook: a single flat sheet named Samples in payload_flat.xlsx, one column per metadata key (_batch_upload_payload.py:181-208).

TIS Scientist: required text attribute, id 91 (tis_schema.json:41-58). A separate optional Contact attribute (id 77) also exists — do not conflate them.

advanced_search response: rows carry {assays, attributeValue, contributor_id, created_at, first_name, id, idlink, idurl, json_metadata, sample_type, sample_type_id, title}. The UID lives in json_metadata.UID; title mirrors it. Observed shape, dev, 2026-07-09 — preserved here rather than normalized into an assumed universal model.

Update gate contract: for each populated-UID row the runner requires the UID to appear in the retrieved manifest with retrieve_status == "verified"; requires the current assay-id set to be a subset of the delivered assay ids unless the UID is listed in --confirm-clear-assays; and refuses to blank any field that is currently present.

15. Security / privacy observations

  • .env holds live secrets (Bedrock bearer token, Anthropic/OpenAI/Google keys, two DB passwords). It is gitignored (.gitignore:18), so it is not committed. Never stage it, and never git add -f it. No secret values are reproduced in this report.
  • Real scientist names from the dev database appear in this report and in docs/research/fixtures/2026-07-09-dev-tis-scientists.json. These are research-staff names on an internal dev instance, not subject data — but the fixture should not leave the repo.
  • The demo replaces a real person's name with Jane Doe in a spreadsheet only. Nothing is uploaded; no NExtSEEK record changes. The skill is structurally incapable of writing (SKILL.md:73-77 plus six independent exit-3 guards).
  • The agent container holds no AWS credentials; the Bedrock token lives only in the proxy sidecar (containers.py:390-393). This demo does not weaken that containment.
  • Credentials were passed to nextseek-init via process environment rather than by editing .env, honoring the file's three-layer protection.

16. Implementation implications

  • No code changes are needed. The demo is environment configuration plus two chat turns. Resist the temptation to "fix" DMAC_OUTPUT_ROOT in code — that redesign is locked, deferred, and already done correctly in the integrated NExtSEEK version.
  • Bring-up order is forced by the dependency graph: make sidecar-build → make sidecar-up (this creates dmac-nextseek-net) → make proxy-build → make proxy-up → launch the bridge. The bridge fail-fasts if the network is missing.
  • The bridge must be launched with an explicit DMAC_OUTPUT_ROOT (Q-003); otherwise the workbook silently lands in ~/dmac-dev/output.
  • .env line 16 must be repointed to https://nextseek-dev.mit.edu — an operator edit, not an agent edit.
  • Verification must not rest on screenshots. Assert the workbook exists at the Dropbox path, then open it and check the Samples sheet actually contains the expected UIDs with Scientist = Jane Doe, and that UID and json_metadata.UID agree. Screenshots are the deliverable for the audience, never the proof.
  • Because turn 1 must yield UIDs that turn 2 consumes, capture turn 1's reply text verbatim; if the NS route returns a prose summary rather than a UID list, turn 2's prompt must carry the UIDs explicitly.

17. Backward-compatibility / migration implications

  • Not applicable to the demo itself — it changes no code, no schema, and no NExtSEEK data.
  • One forward-looking note: the <project>/<user>/<session>/{raw,artifacts} layout locked on 2026-05-28 is a publish-destination change only; ADR-003's containment invariant is preserved under it. When that build lands, DMAC_OUTPUT_ROOT disappears and any launch script pinning it (including README.md:106) must be updated.
  • The stale e2e-local records reference nextseek-sample-read, which no longer exists. They should be treated as historical artifacts, not regression baselines.
