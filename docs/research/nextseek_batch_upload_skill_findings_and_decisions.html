1. Executive summary

The goal is a simple, read-only "payload-builder" skill for the in-container Claude Code agent ("container CC") in dmac_assistant. Given sample information from the user or from the mounted Dropbox project directory, the skill should: (1) fetch the attribute list of the relevant sample type(s) via read-only API calls; (2) build a NExtSEEK batch-upload create/update payload honoring the UID rule (blank UID = new sample, populated UID = update); (3) call the read-only validate endpoint; and (4) return the payload plus the validation verdict to the user for inspection. Performing the actual upload/update (start/) is explicitly forbidden. This is not a full curation skill.

The good news from discovery: the load-bearing piece — the read-only POST /nextseek_api/batch-upload/validate/ endpoint — exists on the upstream dev branch the user pointed at (LOCAL-FIXTURE, verified by git grep origin/dev), and the in-container skill mechanism is well understood (drop a skills/<name>/SKILL.md into the already-baked nextseek plugin; no marketplace or settings edits needed). The hard parts are not "can it be built" but a handful of genuine design choices the repository does not settle.

Open decisions: 3 blockers + 1 execution-blocker + 4 defaultable. The blockers are the payload output format (JSON rows vs xlsx workbook), the read-only API-call mechanism (a read-only POST fights the repo's "POST = write = gated" model), and update-mode attribute handling (a documented silent-data-loss footgun). Delivery is NOT a blocker — the post-turn bridge copier (copier.py + ws.py:296 dispatch_post_turn_copy) is already built and live: the skill writes its payload to /data/scratch and the copier publishes it to the user's delivery folder (Dropbox), so Q-002 is only "what to write." The execution-blocker is how the mandatory live dev-server E2E runs (it incurs paid Bedrock inference and may need VPN). All are in §18.

2. Project purpose as inferred from evidence

LOCAL-FIXTURE dmac_assistant wraps Claude Code as the agent runtime for MIT BioMicro Center lab users: a thin FastAPI bridge authenticates a user, starts a per-user Docker container running claude, and relays stream-json between the chat UI and the agent (.claude/CLAUDE.md "What This System Is"). A per-turn LLM router sends each message to one of three paths: container_cc (general agent work, where skills run), nextseek_query (a thin server-side read-only NExtSEEK query pipeline), or unrelated (a canned reply).

INFERENCE The new skill is a container_cc capability: container CC, driven by a SKILL.md and small read-only CLI tools, turns user/Dropbox sample data into an inspectable, pre-validated NExtSEEK batch-upload payload — without ever writing to the database. This deliberately complements (does not duplicate) the existing read-only query capability and stops short of the host-side dmac-curation-tools "full curation" toolkit.

5. What the code already implements

LOCAL-FIXTURE The NExtSEEK side is fully built and on dev:

  • Validate (read-only): BatchUploadViewSet.validate (batch_upload/views.py:405) runs the pipeline through TRANSFORM and stops before INSERT — no Celery job, no DB write. Accepts rows JSON or multipart .xlsx, requires project_id, takes checks ⊂ {structure, name_check, dag} (default structure). Returns ValidationResult ({valid, summary, errors[], error_groups[], totals, checks_run, checks_skipped}).
  • Sample-type attributes (read-only): GET /nextseek_api/sample_types/ lists types; GET /nextseek_api/sample_types/{uid}/ returns one type WITH its sample_attributes (title/base_type/required/pos/unit/is_title) — the "attribute list" the skill's preliminary step needs (services/sample_types.py:88,114).
  • Upload (FORBIDDEN for the skill): POST .../batch-upload/start/ (views.py:160) — same endpoint for create AND update; UID + update_existing flag decide which.

The dmac side has the in-container plugin scaffolding but no batch-upload / validate / attribute tool yet. Existing nextseek bin tools: nextseek-query, nextseek-api-read (allowlist-gated), nextseek-api-write (confirmation-gated), nextseek-generate-submission (publication submissions — GEO/SRA, a DIFFERENT artifact, not sample batch-upload). The skill therefore needs a new read-only call path (§18 Q-003).

13. Data model / interface summary

Validate request (rows mode): {"project_id": int, "update_existing": bool, "checks": "structure,name_check,dag", "rows": [InputRowModel...]}. InputRowModel (batch_upload/models.py:115): {UID?: str|null, SampleType: str, json_metadata: str (JSON object), assay_ids: int[], project_id?, study_title?/study_id?/sop_id?}; extra="allow". The UID column must equal json_metadata.UID (validator models.py:227-244).

Validate response ValidationResult (models.py:843-866): {valid: bool, summary: str, errors: [{type, message, row, uid}], error_groups: [...], totals: {processed, success, skipped, failed, error, ...}, checks_run: [...], checks_skipped: [...]}. valid = (no errors) AND (totals.error is None).

Two payload shapes (both accepted, do not invent a third): the flat InputRowModel rows (programmatic) and the 4-sheet xlsx workbook Instructions / Samples / Ontology / Assay (the human "Sample Sheet" BMC users upload via the NExtSEEK UI; UID is column 0). A flat single-sheet xlsx (UID, SampleType, json_metadata, assay_ids, ...) is an auto-detected third spreadsheet form. §18 Q-001 chooses which the skill emits.

15. Security / privacy observations

  • No new secrets. The skill reuses the per-session NExtSEEK login already in the container env (NEXTSEEK_USERNAME/NEXTSEEK_PASSWORD), the same Basic-auth pattern as _assistant_client.py. The standing Bedrock-token exfil blocker (OI-3) is unchanged and out of scope here; the skill must not widen it.
  • Structural enforcement of "no upload." A read-only-only bin tool that physically cannot target start/ makes the forbidden-upload guarantee a property of the tool, not just a prompt instruction (favors Q-003 option A).
  • Dropbox is mounted read-only at /data/projects/{name}; the skill must write only to /data/scratch. This intersects directly with Q-002.
  • No PII/secrets surfaced in this report. Credential values were not read; only .env keys/placeholders were referenced.

16. Implementation implications

  • Additive skill, no new route enum. Author build_context/plugins/nextseek/skills/<name>/SKILL.md + read-only bin tool(s); add a route-capability hint; rebuild dmac-assistant:poc; the symlink discovers it. The route-capabilities edit is config-only.
  • The mandatory preliminary attribute fetch maps to GET sample_types/{uid}/ (the retrieve, which carries sample_attributes) — note the read allowlist currently lists only the sample_types/ list, so Q-003 must account for the retrieve path too.
  • project_id resolution is a sub-step, not a question: validate requires the integer SEEK project_id; resolve it from GET projects/ by matching the project name (or the mounted dir name) — deterministic, no user decision.
  • "Fully wired & LIVE" is the acceptance bar. The plan's final task must be a live bridge E2E whose success condition is non-gameable: a saved transcript with exit 0, the captured route_decided.route == container_cc, a captured validate response with valid + checks_run, and a persisted payload artifact — not "looks correct."
  • Do not conflate with nextseek-generate-submission (GEO/SRA publication) — different artifact, different endpoint.

17. Backward-compatibility / migration implications

  • Purely additive — no existing route, tool, or test changes behavior. The only modified shared surfaces are route_capabilities.json (a new task family) and container/CLAUDE.md (a one-line pointer outside the auto-generated NExtSEEK block). No data migration. No format drift: the skill emits one of NExtSEEK's existing accepted payload shapes (Q-001), it does not introduce a new one.
